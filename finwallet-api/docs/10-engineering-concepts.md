# Engineering concepts

Use the questions as interview prompts. Reproduce the examples in a disposable database before explaining why they work.

## HTTP, Spring, and persistence

| Concept | How it works here and why it matters | Exercise, pitfall, and interview prompt |
| --- | --- | --- |
| REST and HTTP methods | MVC routes use GET for reads and POST for new commands. Transfer POST returns 201 even on an exact idempotent replay. See [TransferController](../src/main/java/finwallet_api/transfer/controller/TransferController.java). | Send the same request twice with its original key. Mistake: assuming every POST retry is safe. **Question:** When should a client choose a new key? |
| Dependency injection | Spring discovers beans and supplies dependencies to constructors. The service depends on a repository contract rather than constructing database infrastructure. See [WalletService](../src/main/java/finwallet_api/wallet/service/WalletService.java). | Replace a repository with a mock in a unit test. Mistake: constructing a production service manually and expecting Spring advice. **Question:** What does constructor injection make visible? |
| DTOs and validation | Jackson deserializes requests and Bean Validation checks constraints before service execution. Funding also checks JSON token types and allowed fields during deserialization. See [FundingRequest](../src/main/java/finwallet_api/funding/dto/FundingRequest.java). | Try `10000` and `"10000"`. Mistake: allowing coercion across a payment boundary. **Question:** Which rules belong in the DTO versus the service? |
| JPA and Hibernate | Mappings associate objects with rows. Managed objects are dirty-checked and repository queries can project DTOs directly. See [Wallet](../src/main/java/finwallet_api/wallet/entity/Wallet.java) and [TransferRepository](../src/main/java/finwallet_api/transfer/repository/TransferRepository.java). | Trace an admin status update from managed entity to SQL. Mistake: serializing persistence entities as the API contract. **Question:** When are dirty changes flushed? |
| SQL constraints and indexes | Constraints reject invalid persisted state, while indexes help locate records and enforce uniqueness. See [V5](../src/main/resources/db/migration/V5__unique_ledger_entry_type_per_transfer.sql) and [V6](../src/main/resources/db/migration/V6__index_transfer_history.sql). | Compare a journal uniqueness check and a history ordering index. Mistake: assuming every foreign key automatically creates an index. **Question:** What invariant can a unique index enforce under concurrency? |
| Exception handling | Controller advice maps domain exceptions to HTTP status codes. Recognized persistence errors produce a generic message. See [GlobalExceptionHandler](../src/main/java/finwallet_api/common/exception/GlobalExceptionHandler.java). | Trigger an insufficient-funds 422. Mistake: exposing SQL errors or parsing every error as JSON. **Question:** Where should a database failure become an HTTP error? |
| Integration testing | Spring and a real PostgreSQL instance exercise wiring, migrations, constraints, and locking. See [FundingIntegrationTest](../src/test/java/finwallet_api/funding/FundingIntegrationTest.java). | Run a mocked settlement test and its PostgreSQL counterpart. Mistake: treating mock tests as evidence of row-lock behavior. **Question:** What failures does an integration test catch that a mock cannot? |

## Transactions and concurrency

| Concept | How it works here and why it matters | Exercise, pitfall, and interview prompt |
| --- | --- | --- |
| ACID | Atomicity keeps wallets and journals together. Constraints support consistency, locks and snapshots provide isolation, and PostgreSQL commits durable state. See [FundingSettlementService](../src/main/java/finwallet_api/funding/service/FundingSettlementService.java). | Trace what a journal failure rolls back. Mistake: treating two wallet writes as independent transactions. **Question:** What should remain after an exception before commit? |
| Transaction proxies | Spring intercepts calls to managed beans to start, join, or suspend a transaction. See `REQUIRES_NEW` in [FundingSettlementService](../src/main/java/finwallet_api/funding/service/FundingSettlementService.java) and `MANDATORY` in [FundingJournalRepository](../src/main/java/finwallet_api/funding/repository/FundingJournalRepository.java). | Draw the transaction around settlement and journal append. Mistake: relying on self-invocation to apply a new transaction. **Question:** What happens when a caller already holds the target lock? |
| Isolation | READ COMMITTED checks committed data across statements. REPEATABLE READ keeps a stable snapshot for history and reconciliation. See [TransferHistoryService](../src/main/java/finwallet_api/transfer/service/TransferHistoryService.java). | Consider a new transfer arriving between a history page and its count query. Mistake: expecting two separate page requests to share a snapshot. **Question:** Why use a snapshot for reconciliation? |
| Pessimistic locking | The wallet repository acquires a write lock before reading mutable balance for posting. Writers on that row wait for commit. See [WalletRepository](../src/main/java/finwallet_api/wallet/repository/WalletRepository.java). | Trace two simultaneous debits against RM100. Mistake: checking balance before acquiring the lock. **Question:** When is a pessimistic lock preferable to an optimistic retry? |
| Race conditions | A check followed by a write can race another request. FinWallet checks available balance and replays under the wallet lock and uses relational uniqueness. See [TransferConcurrencyTest](../src/test/java/finwallet_api/transfer/TransferConcurrencyTest.java). | Run the overspend test. Mistake: assuming a transaction alone makes check-then-write safe. **Question:** Where is the shared state serialized? |
| Deadlocks | Two transactions can each hold the row the other needs. Transfers lock lower wallet ID first. See [TransferService](../src/main/java/finwallet_api/transfer/service/TransferService.java). | Draw A-to-B and B-to-A lock order. Mistake: always locking the sender first. **Question:** How do locks across multiple modules affect deadlock risk? |
| Idempotency | The same business intent uses a stable key in its owner scope. The service compares stored inputs under a lock and replays the original result. See [FundingService](../src/main/java/finwallet_api/funding/service/FundingService.java). | Simulate a lost response and resubmit with the same key. Mistake: creating a new key after a timeout. **Question:** Why compare the payload as well as the key? |

## Money, accounting, and security

| Concept | How it works here and why it matters | Exercise, pitfall, and interview prompt |
| --- | --- | --- |
| Integer minor units | The API uses JSON integer sen and PostgreSQL BIGINT. The funding script converts decimal text exactly. See [dev-fund-wallet.sh](../scripts/dev-fund-wallet.sh). | Convert RM10.50 to 1,050 sen. Mistake: using binary floating point or ignoring client safe-integer limits. **Question:** Is a positive integer sufficient to validate a transfer? |
| Double-entry bookkeeping | A posting debits one account and credits another by the same amount and currency. A simulated deposit credits the wallet and debits simulated settlement. See [FundingJournalRepository](../src/main/java/finwallet_api/funding/repository/FundingJournalRepository.java). | Write the two legs for RM100 funding and RM30 transfer. Mistake: creating a single credit because only one customer wallet changed. **Question:** What does the counter-account represent? |
| Ledger entries | Journals store posted effects with operation references and account identity. A reversal creates a new linked posting. See [LedgerEntry](../src/main/java/finwallet_api/transfer/entity/LedgerEntry.java) and [Reversal design](transfer-reversals.md). | Rebuild Alice’s RM70 from +10,000 and −3,000. Mistake: rewriting the original debit for a reversal. **Question:** How do immutable postings support investigation? |
| Data integrity | Validation, checks, foreign keys, paired postings, and read-only reconciliation protect different invariants. See [LedgerReconciliationService](../src/main/java/finwallet_api/reconciliation/service/LedgerReconciliationService.java). | Compare posted balance to journal sum and available balance to reserves. Mistake: treating a successful commit as proof of accounting consistency. **Question:** Which discrepancies can reconciliation detect that a uniqueness constraint cannot? |
| BCrypt and JWT | BCrypt stores a salted password hash. JJWT creates a signed bearer credential with expiry after login. See [PasswordEncoderConfig](../src/main/java/finwallet_api/common/config/PasswordEncoderConfig.java) and [JwtService](../src/main/java/finwallet_api/common/security/JwtService.java). | Log in, then test expiry using a local short lifetime. Mistake: treating a JWT signature as encryption. **Question:** What changes after signing-key rotation? |
| Authentication and authorization | Authentication establishes identity. Authorization checks owner or role access using current database state. See [JwtAuthenticationFilter](../src/main/java/finwallet_api/common/security/JwtAuthenticationFilter.java) and [SecurityConfig](../src/main/java/finwallet_api/common/security/SecurityConfig.java). | Call an admin route with an ordinary user’s token and expect 403. Mistake: trusting a role supplied by the client or accepting any wallet ID. **Question:** Why can the same JWT produce a different decision after a database role change? |
